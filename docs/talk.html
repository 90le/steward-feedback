0:00–1:30

先让听众知道用户要办什么事

讲者提示从一个群内反馈场景讲起，再指三块分工。Issue 是事项单，PRD 是需求说明书。

口播参考 · 可改成自己的表达

先设想一个日常场景。你在群里发现功能有问题，或者想提一个新需求。有人需要听懂你说的是什么，补齐缺的信息，检查是否已经有人提过，写成可执行的需求，再跟进结果。

这些动作交给几位 AI 后，我们还要解决一个问题：谁负责接下一步，依据的是哪一版，哪项检查真的做过，最后要回给谁？这就是我们做 Steward 的原因。

图上 OpenClaw 是运行基础，提供模型、会话和工具。五个 Agent 是具体执行角色。Steward 是我们写的业务插件，负责保存进度、检查条件和安排交接。稍后我会用两个例子说明这些分工怎样产生了实际结果。

为了方便理解，接下来提到的 Issue 可以当作一张可追踪的事项单；PRD 就是需求说明书。我们先看内容发生了什么变化，不需要先记住所有英文名。

1:30–4:00

#9：一次打回怎样保护用户的决定

讲者提示按首稿、评审、修订讲。打开首次独立评审与第二版交付，留约 30 秒看前后变化；随后回到本页。

口播参考 · 可改成自己的表达

第一个需求是临时置顶自动到期。比如一场活动结束了，它的通知还长期挂在群顶部，就要有人回来清理。用户希望设置一个未来时间，到时取消置顶；原消息继续保留，群里也不多发一条提醒。

小丘先澄清范围、查重并登记。小助写了第一版需求说明，其中加入“本期不提供批量到期管理”。这句话听起来像在控制范围，但它实际上替用户作了一个未确认的决定。

现在看这条评审。小衡指出，用户没有讨论过批量入口，既不能推定要做，也不能推定已经同意排除。小助在第二版中撤下这项非目标，把它改成需要确认的问题。

请注意这里的分工：小助负责把需求写清楚，小衡负责用原始诉求检查它。小衡没有因为文档写得完整就放行。我们也保留了首稿和打回理由，所以可以解释第二版为什么变成现在这样。

第二版通过以后，程序才接续安排开发、独立测试和复核。这项案例要说明的工程价值，是作者和评审者分开工作，并且每一轮都绑定具体版本。多一个角色是否有用，要看它是否发现问题、是否改变结果，这里有可核对的证据。

4:00–7:00

#10：接口通过后，继续实际操作

讲者提示打开早期浏览器反馈，只指一处失败。再看第六版交付，区分小检的测试与建设任务的追加验收。

口播参考 · 可改成自己的表达

第二个需求叫“稍后再提醒”。用户暂时忙，希望自己的提醒晚一点再出现。它只影响本人，不改动原群消息，也不影响其他人的提醒。

讨论中又补充了一个场景：我可能先在另一处处理完这件事。因此需求要分清两种动作。只是查看原消息，延后安排继续有效；明确标记已经处理，就取消延后，不应该到时间又把同一件事推回来。

第二版演示已经有独立 HTTP 测试。我们再从浏览器点进去，发现默认的“15 分钟后”竟然会失败。原因是页面和后台使用了不同的时间约定；测试给后台的参数，与页面实际发出的参数不一样。

另一个按钮写着“查看原消息”，点下去却只出现“已定位”的提示，用户还是看不到原文。按钮有文字、接口有返回，都不足以证明用户完成了这一步。

修到第三版后，这两点改善了，但我们又看到状态不一致：另一页已经把提醒标为已处理，本页刷新后却仍显示未处理。页面用了自己的初始数据，没有展示后台已经保存的事实。

第四版修复了当时的跨页与重载问题。后来我们故意放慢输入，停留超过三秒，才发现页面定时刷新会把正在编辑的时间覆盖掉。这个问题在原始页面、受限静态预览和可信后端中都能复现，不能把它归咎于新安全包装。

第五版保留了编辑草稿，但后端页面发送的 Accept 请求头不符合已声明的预览桥协议；“五秒后”按钮又把秒数截掉，算成了过去的整分钟。静态页面的一组检查通过，并不能代替后端联调和短时操作。

第六版开发实际拿到了第五版的三个正式源文件，共 46,333 字节，完整内容和摘要都已核对。小码据此增量修正，保留原件和作者记录，再交给独立测试与复核。最终小检的 HTTP 7 项、建设任务可信后端浏览器 30 项、静态浏览器 25 项分别通过，覆盖了双页面、失败重试、真实到期和输入保留等路径。

这个例子说明两件事。第一，测试要覆盖用户实际走的路径，不能用一份另外拼好的请求代替页面。第二，协作流程要能够接住交付后的纠错。完成一份首稿以后，新的证据还应该推动下一轮工作，而不是只能重新开一个孤立任务。

7:00–9:00

看分工：哪一部分是谁做的

讲者提示沿五个角色从左到右讲，再说明 Octo 入口、GitHub 记录和原会话回报。手机上按从上到下的顺序读。

口播参考 · 可改成自己的表达

看过例子后，再看系统分工就容易理解了。Octo 是用户提出问题的地方。消息进入运行中的 OpenClaw 后，Steward 记录可信的来源和当前任务，按职责安排 Agent。

小丘负责问答、澄清和反馈入口；小助整理需求；小衡独立评审；小码开发演示；小检执行独立测试。GitHub 保存需求、评审、代码和报告。最后由既定的消息出口把结果送回原会话。

这里有两类资料。源码和知识帮助 Agent 判断产品事实；数据库记录这件事做到哪一步、有没有等待中的运行、哪些通知还没确认。把这两类信息分开，才不会把聊天里的“我做完了”误当作实际工作状态。

当前我们用一个 Gateway、一个业务插件和一份业务数据库承载主路径。Worker 是插件里的调度程序，不是另一位模型领导者。它按照已记录的阶段派任务，五个 Bot 不需要在群里互相接话才能继续工作。

9:00–11:00

程序在交接时检查什么

讲者提示先讲当前版本的独立评审，再讲可信来源与实际回执。强调阶段检查仍需要内容复核。

口播参考 · 可改成自己的表达

我们没有规定 Agent 查第一个文件之后只能查第二个文件。它可以多轮搜索，发现信息不够后继续读取，也可以根据证据改变判断。

程序检查的是工作交接的前提。例如，建单需要真实来源和有效查重依据；需求就绪需要对应版本的独立评审；演示交付要绑定已经测试的候选；消息完成要有实际回执。前提缺失时，程序不会把它推进成完成状态。

再看来源。群里可能有两个人交错发消息，后台任务可能过几分钟才结束。此时不能看“最近一句是谁说的”决定回给谁。Steward 把原消息、提出者、位置和任务关联起来，后续仍沿原来源回去。

如果一次外部请求超时，也不能马上再发一遍。远端可能已经完成，只是返回结果丢了。程序要先核对原操作，再决定是否继续。这样才能降低重复建单和重复回报的风险。

这些检查能约束角色、版本和外部动作。它们不能替代内容判断，所以我们仍需要独立评审，也需要刚才看到的浏览器复验。

11:00–12:30

谁能找哪位 Agent，能让它做什么

讲者提示先讲普通用户入口，再讲直接调度的配置权限。身份准入之后还要检查具体动作。

口播参考 · 可改成自己的表达

普通用户可以找小丘问产品问题、提交反馈和查状态。配置中的负责人、观察者，以及明确放行的外部测试 Bot，可以向其他角色提出职责范围内的任务。未放行的 Bot 不会因为在群里发了一句话就得到团队响应。

小测能够参与测试，依据的是配置中的真实身份。它与小码、小检分开，避免让同一角色既提供测试输入，又开发、测试并证明自己的结果。

准入也只是第一层。即使允许提出任务，仍要遵守角色、阶段和资源边界；它不能随意更换目标仓库、读取凭证或跳过独立检查。普通用户的反馈可以进入预先授权的固定流程，但普通用户不能直接指挥开发或审批角色。

资料方面，Agent 可以读取需要的源码和共同知识；产物写入指定位置；凭证和运行配置留在它们不应接触的管理范围。权限是否可用、是否越界，要以实际工具与环境检查为准。

12:30–14:00

知识为什么需要版本与重新取证

讲者提示从一次任务的依据讲到上游变化，再讲重新调查与发布。举“能打开引用但可能漏条件”的例子。

口播参考 · 可改成自己的表达

知识库帮助 Agent 找到资料，但源码会变化。如果只刷新文档日期，旧结论并不会因此变成新结论。

我们让一次任务使用一致的源码版本，并记录它绑定哪份知识。发现上游变化后，相关知识进入待审，由作者和独立评审重新调查，再整体发布。旧任务继续保留自己的依据，新任务读取适合它的版本，避免把不同时间的材料混在一起。

还有一个容易误解的地方：引用可以打开，回答仍可能有错。某段代码是真实的，但结论可能漏掉配置条件、调用方或例外。程序可以检查路径、行号和版本，却不能单靠这些信息判断概括是否充分。

因此我们把引用检查和内容复核分开记录。遇到“这台实例现在有没有开启某项功能”，还要找部署和运行证据，不能把主分支里的实现直接说成实例现状。

静默扫描、缓存与恢复

讲者提示分别指有变化、无变化和请求失败。缓存的固定场景结果不能当作线上整体节省比例。

口播参考 · 可改成自己的表达

真实工作还需要在没人提醒时继续。Steward 定期检查需求池和资料是否发生变化。有新的需求或意见时，再安排模型理解和处理；没有变化也留执行记录，但不在群里反复播报“一切正常”。

缓存优化解决的是重复读取。多次查询同一份已验证资料，可以短期共享结果；评论没有变化时，可以避免重复传输正文。但缓存缺失或不完整，就要重新读取，关键写入之前也要核验依据。

为什么经历三次工程选择

讲者提示依次讲各版本解决了什么、接通了什么、维护代价是什么。参考来源只讲方法。

当前结构经过了三轮工程选择。V1 已经有真实协作、Hook 和脚本，也吸收了既有知识工程、团队工程参考资料和协作治理参考项目的方法。它的问题是规则分散在多个地方，角色文档、定时提示和运行配置越来越难保持一致。

V2 把身份、事件、权限和恢复设计得更完整，也做出了实质代码。但需要接通的适配器和运行边界更多，一些角色声明了能力，实际工具和环境还没有准备好。设计范围与真实业务接通速度开始脱节。

用户随后选择收敛到 MVP。我们先完成三角色的支持与需求闭环，再按实际演示交付需要增加开发和独立测试。扩成五角色以后，仍沿用同一个插件、业务库和来源机制。

所以比较版本时，要同时看解决了什么、实际接通了什么，以及维护成本。不能按 Agent 数量判断谁更好，也不能把先前版本的有效成果一笔抹掉。

当资料不足时，小丘要说明不知道哪部分、需要补什么证据，以及应向谁求助。负责人从配置中确定，通知仍按原会话规则处理。求助已经发出，只能说明通知的状态，不能说人已经接手或问题已经解决。
