# Octo 小码（runtimeId: implementation）

PRD v4 · 候选 r1

# 提醒 · 稍后再提醒（snooze）演示 v4

对应 PRD：Issue #10 v4。本原型演示"在自己的提醒列表内对属于本人的提醒设置稍后再提醒"的用户可感知结果，覆盖 v4 的 AC1–AC16（包括到点重现、真实定位原消息、明确处理即取消延后、仅查看不视为处理、多端一致等）。仅前端/后端演示，未接入任何真实用户系统或 Octo 上游。

## 文件

- `index.html`：单文件前端（HTML/CSS/原生 JS），无外链、无 iframe、不读 cookie、不联网。
- `server.mjs`：Node 内置 http 服务，处理内存中的模拟数据。GET `/` 返回前端并注入 `data-api="1"` 以启用联调模式。
- `README.md`：本文件。

## 启动

需要 Node 24（不安装任何依赖）。

```
# 仅打开静态预览（无后端，前端使用本地模拟数据，可完整操作）
# 直接用浏览器打开 index.html 即可。

# 启动联调（前后端一起跑）
node server.mjs
# 或指定端口
PORT=4000 node server.mjs
# 然后浏览器访问 http://127.0.0.1:3000/  （或对应端口）
```

`server.mjs` 使用 `import.meta.url` 相对定位同目录下的 `index.html`，因此从任意工作目录（含 `/tmp`）执行均可，只要 `index.html` 与其在同一目录。

## 模式差异

前端根据根 `<html>` 是否具有 `data-api="1"` 决定运行模式：

- **本地模拟（静态预览）**：任何来源打开 `index.html` 时都可用，所有操作在浏览器内存中执行。
- **联调（服务器）**：`server.mjs` 在 GET `/` 返回 HTML 时注入 `data-api="1"`，前端改为 `fetch` 同源 `/api/...`。服务端在内存里执行业务校验并返回真实结果，前端根据服务端结果刷新视图。

两种模式共享同一套接口语义，可用同样的验收步骤操作。

## 模拟身份

无密码、无外部认证。顶部"当前身份"下拉切换：

- `u_alice` Alice —— 主要演示对象（拥有 `r_a1`、`r_a2` 两条提醒）。
- `u_bob` Bob —— 其他成员（拥有 `r_b1`、`r_b2`），用于验证"仅影响本人"。

服务端在每次 API 调用时通过 `X-Acting-User` 或请求体 `actingUserId` 独立校验身份，前端"隐藏按钮"只是 UX，业务边界由服务端自行判断（例如即便手写请求也不能操作他人提醒）。

## HTTP 接口（仅演示，不对外发布）

所有业务接口为 `POST /api/<op>`，请求体 JSON，响应 `{ ok:true, data:{...} }` 或 `{ ok:false, error:{ code,msg,... } }`，均携带 `serverNow`。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET  | `/`               | 返回带 `data-api="1"` 的前端 |
| GET  | `/api/health`     | 健康检查 |
| POST | `/api/list`       | 列出当前身份的提醒（含到点重现视图状态） |
| POST | `/api/snooze`     | 设置或修改稍后再提醒时间 |
| POST | `/api/cancelSnooze` | 取消延后 |
| POST | `/api/markDone`   | 明确标记为已处理（active/snoozed 均可） |
| POST | `/api/viewMessage`| 查看原消息（返回消息与会话上下文；不改变提醒状态） |
| POST | `/api/reset`      | 重置内存数据（仅演示） |

所有修改类接口在校验失败（如 `time_invalid`、`forbidden`、`invalid_state`）时保持数据原状态，前端据此提示失败并回读最新状态，避免出现"看似生效但实际未保存"的错位。

## 原型与真实功能的边界

- 数据存储在服务进程内存中，进程重启或调用 `/api/reset` 后数据回到初始种子；没有任何持久化，也不会写入宿主。
- 用户与消息均为硬编码的模拟数据；不接入 Octo 真实的账号系统、群消息、@ 关系、未读/置顶等状态，也不会向真实群或用户发送任何通知。
- "多端一致"通过同一后端进程的内存状态与客户端刷新演示：切换身份 = 切换端，"刷新"按钮 + 每 3 秒轮询模拟 v4 AC15/AC16 的"另一端处理后本端看到已处理"效果；PRD 明确不规定具体同步机制（NG8/OQ11），本原型不代表最终产品的一致性方案。
- "到点重现"由服务端每次 `list` 时按 `snoozeUntil <= now` 派生视图状态实现，仅用于展示 R3；并非产品级调度器。
- 时间校验以服务端 `Date.now()` 为唯一基准；失败响应会返回 `serverNow`，前端在 toast 中展示，供用户按服务端时间重新选择（对齐 AC13）。
- 前端不发起任何跨域请求、不加载任何外部字体/脚本、不使用 iframe、不读写 cookie/localStorage。

## 手工验收步骤（对齐 AC1–AC16）

打开 `http://127.0.0.1:3000/`（联调）或直接双击 `index.html`（本地模拟）。默认身份 Alice。

1. **AC1** 对 `r_a1`（Alice 的提醒）点"稍后再提醒" → 选"15 分钟"或输入未来时间 → 确定；列表徽章变为"延后中"。
2. **AC2** 切换到 Bob；`r_b1`/`r_b2` 仍为未处理，未受 Alice 操作影响。
3. **AC3** 将某条 snoozeUntil 手动设为 1 分钟内（快捷 15 分钟不便验证，可打开开发者控制台调用 `fetch('/api/snooze', ...)` 或在本地模拟模式设短时间；亦可等待 3 秒轮询）。到点后徽章变为"未处理（已到点重现）"。点"查看原消息" → 右侧真实展示原消息内容并高亮定位在会话中，含"已定位到原消息"提示。
4. **AC4** 对延后中的提醒点"修改延后时间" → 选新的未来时间 → 确定；`再次提醒`时间更新。
5. **AC5** 对延后中的提醒点"取消延后" → 立刻恢复为"未处理"。
6. **AC6** 全过程右侧会话区不新增系统消息，原消息内容/顺序无变化。
7. **AC7** 打开稍后再提醒表单，把"自定义时间"改成过去时间 → 确定 → toast 提示"再次提醒时间必须晚于当前时间（服务器当前时间 ...）"，提醒保持原状态。
8. **AC8** 联调模式下停止 `server.mjs`（Ctrl+C）后再点"稍后再提醒"→ toast 显示"网络错误"，前端刷新回退到最近一次已知状态；重启服务后再操作恢复正常。
9. **AC9** 切换到 Bob，无法看到 Alice 的提醒；即使手工 `curl -X POST http://127.0.0.1:3000/api/snooze -H 'x-acting-user: u_bob' -d '{"reminderId":"r_a1","snoozeUntil":9999999999999}'` 也返回 `forbidden`。
10. **AC10** Alice 对延后中的提醒点"标记为已处理" → 徽章变"已处理"；到点后不重现。
11. **AC11** Alice 对延后中的提醒仅点"查看原消息" → 状态与再次提醒时间不变；到点仍重现为未处理。
12. **AC12** AC10/AC11 之后切到 Bob，`r_b*` 未变化。
13. **AC13** 快捷"15 分钟"始终成功；若手动填入小于服务端 now 的时间，toast 会显示服务端 now 供用户重新选择。
14. **AC14** 见 AC3、AC11 组合验证。
15. **AC15/AC16** 联调模式：在浏览器窗口 1（身份 Alice）对 `r_a1` 标记已处理。在窗口 2（新开窗口/隐身模式/其他浏览器）以身份 Alice 打开同一地址：列表显示 `r_a1` 已处理；等到原定 snooze 时间不会重现。窗口 1 点"刷新"或等待 3 秒轮询也保持一致。任何时刻切换身份或刷新，界面显示的状态与服务端 `list` 返回的最新真实状态一致（可展开左侧"调试信息"查看 `status`/`viewStatus`）。

## 已知边界

- `snoozeUntil` 使用 `datetime-local`，粒度为分钟；服务端接收毫秒时间戳，任何小于当前 `Date.now()` 的值都会被拒绝。
- 多标签一致性通过每 3 秒的 `list` 轮询演示；`NG8`/`OQ11` 明确 PRD 不固化机制。
- 未实现批量、循环 snooze、桌面推送、原消息撤回等（对应 NG4/NG5/OQ4/OQ5），符合 PRD 非目标范围。
