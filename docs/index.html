01 / 从零读懂 Steward

Steward 是带着 Agent 团队办事的流程程序

它知道事情做到哪一步、下一步交给谁、还缺什么条件，以及结果有没有真的落地。

讲者辅助 先说人话，再按需要展开技术

先用一句话定义：Steward 是把 Agent 团队的工作接起来的程序。模型负责理解和产出，它负责保存进度、检查条件和回报。今天要看的，是一条事情怎么被完整处理的工作链。

怎么展开这一章把 OpenClaw、Steward、五个 Agent、Octo 和 GitHub 分开指给听众。不要把平台能力和我们编写的业务控制混成一个东西。

这句话要说准不要把 Steward 说成更聪明的第六个 Agent，也不要说程序可以替模型判断所有问题。

管流程、派任务、验结果，记住工作进度。

在群里听到五个 Bot 说话很容易，难的是持续知道：谁提出了问题、哪份需求经过确认、谁独立检查过、哪一版真的测试了、结果最后回给谁。Steward 把这些事实接成可以继续推进的工作链。

技术上，Steward 是运行在 OpenClaw 中的轻量业务插件。OpenClaw 提供模型、会话、工具和沙箱能力；Steward 组织这些能力，处理 Octo 的产品问题与需求。小丘等五个 Agent 是执行角色，Worker 是插件中的调度代码。

运行基础

OpenClaw

启动与运行 Agent，提供会话、工具调用和原生沙箱。它解决“Agent 怎么运行”。

业务组织

Steward

检查来源和阶段，安排角色，保存任务与外部效果。它解决“这件事怎样继续推进”。

具体工作

五个 Agent

理解用户、调查资料、判断重复、起草与评审、开发与测试。它们决定“怎样做好当前任务”。

阶段内自主调查，阶段之间必须满足条件。
这句话概括了本项目的设计：模型仍然可以多轮搜索、读文件、调整判断和自然组织语言；必要的业务阶段、权限与完成条件由程序执行。

最初目标是产品支持与需求协作。当前五角色又把已通过评审的需求延伸到可运行演示，仍保留清楚的范围：演示前后端与生产产品是不同交付，上游 octo-server 保持只读。

容易混同的三种参与者本项目中的作用
Steward 产品团队实际在 OpenClaw 中运行的小丘、小助、小衡、小码、小检。
建设与验收工具编写 Steward、调查历史、修复控制器和追加浏览器验证的开发助手及管理任务。
外部测试提问者被配置放行的小测，提供真实输入；不兼任开发或独立测试角色。

谁完成了哪项验证要分开署名。建设助手自己的操作，不冒充产品 Agent 自治完成。

03 / 三次工程选择

从复用资产，到扩展设计，再收敛真实交付

V1、V2、MVP 是这里对工程阶段的称呼。比较时看职责覆盖、实施负担、维护成本和真实完成程度，不按 Agent 数量判断优劣。

讲者辅助 先说人话，再按需要展开技术

V1 并不是一无所有，它已经能协作，也有 Hook 和脚本。V2 把边界设计得更完整，但需要接通的东西更多。MVP 把运行路径缩小，先证明一条业务，再沿现有结构增加开发和测试。

这句话要说准不要用角色数量排名，也不要把“时间紧”当作停止 V2 的唯一原因。

04 / 历史资产怎样复用

借鉴的是可验证的方法，落地仍要重做真实接线

已有项目帮助我们少走弯路，但阅读、借鉴、安装和实际运行是四种不同状态。治理思路在 V1 就已出现，并不是 V2 才引入。

讲者辅助 先说人话，再按需要展开技术

我们没有从零发明每条规范。已有项目教会我们怎样分资料、怎样交接、怎样定义角色和验证完成。这里采用的是有用的方法，真正对接 OpenClaw 和 Octo 仍需要实现与验收。

怎么展开这一章沿参考资产→方法→本项目落点看。私有知识仓的价值讲组织经验，不展开私人设备事实。

这句话要说准不要把只读参考说成整套安装，也不要说当前 Agent 直接连着所有私人知识库。

已有工程经验→选择适合的规则→对接真实平台→用运行结果核对

08 / 必要流程与程序门控

程序门控：条件没满足，任务不能往下走

“必须先第一步、再第二步，否则打回”可以描述必要业务阶段，但应保留阶段内的自主调查和正常分支。

讲者辅助 先说人话，再按需要展开技术

这不是让 AI 每一步只能点一个按钮。它在阶段里可以自主查资料；但要建单、说 PRD ready、发布演示或确认送达，必须拿出各自的依据。

读图顺序每个关口只回答“拿什么才能继续”，用 #9 的独立打回来展示真的改变了结果。

这句话要说准Hook 也能强制拦截，不能说知识库加 Skill 加 Hook 都只有软约束；也不能把通过格式校验等同于语义正确。

我们把关键流程写进 Steward。Agent 提交调查和产物，程序检查谁在做、做到哪一步、依据是否有效、结果是否真实，再安排下一步。

知识与 Skill：支持“怎样做好”

提供产品材料、调查方法、职责与质量要求。如果“先查重”“不能泄露”只出现在文本中，执行主要依赖模型遵守指引。

状态机与检查：决定“能否继续”

核对原始来源、任务角色、当前阶段、有效查询和产物版本；不满足条件时，工具或状态转移直接拒绝。模型的一句“通过”不能替代这些记录；记录齐全也不能代替内容质量与真实使用验收。

Hook 本身也能实施强制约束。不能把“知识库＋Skill＋Hook”一概等同于模型自觉。我们仍使用这些能力，差别在于关键规则是否落实为可执行检查，而不是组件的名字。

结论是否切题、测试是否充分、交互是否符合用户目标。

09 / 原消息到真实回执

回复谁、引用哪条消息，不能靠模型猜

同一个人连发两句、多人交错、两个私聊同时进行时，“最近一条消息”会失去可靠性。Steward 把真实来源作为任务的一部分保存。

讲者辅助 先说人话，再按需要展开技术

群里两个人交错提问时，不能凭最后一句是谁决定回给谁。我们把原消息的身份和位置跟任务一起保存，后面异步几分钟也能沿原来源回去。

读图顺序强调输入保存、模型完成、远端写入与原目标会话读回。平台读回不等于对方设备已经展示或已读；超时后先查再重试。

这句话要说准别把一次发送返回、一个内部任务 ID 或一个数据库状态当作实际送达。

多人重复反馈

两个用户可以关联同一个 Issue，业务事项合并，来源与订阅仍分别保留。不能因为已有一条通知，就把另一个提出者的回执省掉。

发送结果不确定

接口超时可能发生在远端已成功之后。先按原效果和标记核对；不能直接再建一单或再发一条，把超时变成重复业务。

展开：幂等、意图与回执的区别

意图记录“准备做什么”，幂等标识记录“这是否同一件操作”，回执记录“外部实际发生了什么”。这三者在重试、限流和断线时各有作用。

原消息来源在入站闭包中关联实际运行，再用于工具检查和回复。账号／群／私聊的隔离依赖原生上下文与程序记录；仅在提示词里写“别串消息”不等于实现了该机制。

展开：当前沙箱与出口保护的实际范围

小码和小检的命令工具强制在原生 Docker 中执行，关闭提权和网络，使用非 root、只读根目录及资源限制。各自 /artifacts 可写，冻结 /candidate 只读；不挂载宿主配置、凭证、原生会话历史目录或 Docker socket。

沙箱中的 /source 是独立只读导航快照，不承诺随上游实时刷新。正式源码引用仍需要通过本轮版本绑定工具取证。其余三个角色保留受限读取与专用业务工具，没有为扩员统一开放 Shell。

Gateway 中的插件不受 Agent 沙箱自动约束，因此插件的凭证、目标和路由限制继续独立存在。消息出口检查正文、引用、预览和异步通知；敏感候选的阻止或替代提示不作为原业务成功。

这些是当前配置和已测范围。普通人跨角色入口限制有代码回归，真实未配置人现场覆盖仍单独待补。当前 /artifacts 是角色级共享根，/candidate 也是共同只读候选根；任务或租户间保密需要更细粒度设计。

展开：实际工具入口与按需调查能力

当前模型使用六个业务工具入口。一个入口可以提供多种调查方式，数量不代表只能调用一次。资料不足时先区分没有查全、调用方法不对、工具失败和权限拒绝，再决定怎样补齐。

点击 案例 #9，停在 #9。按“用户问题→首稿→打回→修订”读表。打开 首次独立评审，只指其中一条打回理由；再打开 PRD v2 的修订记录。留约 30 秒让听众看前后变化。

第一个需求是临时置顶自动到期。比如一场活动结束了，它的通知还长期挂在群顶部，就要有人回来清理。用户希望设置一个未来时间，到时取消置顶；原消息继续保留，群里也不多发一条提醒。

小丘先澄清范围、查重并登记。小助写了第一版需求说明，其中加入“本期不提供批量到期管理”。这句话听起来像在控制范围，但它实际上替用户作了一个未确认的决定。

现在看这条评审。小衡指出，用户没有讨论过批量入口，既不能推定要做，也不能推定已经同意排除。小助在第二版中撤下这项非目标，把它改成需要确认的问题。

请注意这里的分工：小助负责把需求写清楚，小衡负责用原始诉求检查它。小衡没有因为文档写得完整就放行。我们也保留了首稿和打回理由，所以可以解释第二版为什么变成现在这样。

第二版通过以后，程序才接续安排开发、独立测试和复核。这项案例要说明的工程价值，是作者和评审者分开工作，并且每一轮都绑定具体版本。多一个角色是否有用，要看它是否发现问题、是否改变结果，这里有可核对的证据。

回到 02 两条案例。若听众问“是不是任何未提到的功能都要做”，回答：未讨论的部分保留待确认，并不自动进入实现范围。

4:00–7:00｜#10：为什么接口通过以后，还要实际操作页面

在 案例 #10 移到 #10。打开 v2 浏览器反馈，再看 v3 的一致性反馈。每次只指一处现象，不读代码与时间戳。

第二个需求叫“稍后再提醒”。用户暂时忙，希望自己的提醒晚一点再出现。它只影响本人，不改动原群消息，也不影响其他人的提醒。

讨论中又补充了一个场景：我可能先在另一处处理完这件事。因此需求要分清两种动作。只是查看原消息，延后安排继续有效；明确标记已经处理，就取消延后，不应该到时间又把同一件事推回来。

第二版演示已经有独立 HTTP 测试。我们再从浏览器点进去，发现默认的“15 分钟后”竟然会失败。原因是页面和后台使用了不同的时间约定；测试给后台的参数，与页面实际发出的参数不一样。

另一个按钮写着“查看原消息”，点下去却只出现“已定位”的提示，用户还是看不到原文。按钮有文字、接口有返回，都不足以证明用户完成了这一步。

修到第三版后，这两点改善了，但我们又看到状态不一致：另一页已经把提醒标为已处理，本页刷新后却仍显示未处理。页面用了自己的初始数据，没有展示后台已经保存的事实。

第四版修复了当时的跨页与重载问题。后来我们故意放慢输入，停留超过三秒，才发现页面定时刷新会把正在编辑的时间覆盖掉。这个问题在原始页面、受限静态预览和可信后端中都能复现，不能把它归咎于新安全包装。

第五版保留了编辑草稿，但后端页面发送的 Accept 请求头不符合已声明的预览桥协议；“五秒后”按钮又把秒数截掉，算成了过去的整分钟。静态页面的一组检查通过，并不能代替后端联调和短时操作。

第六版开发实际拿到了第五版的三个正式源文件，共 46,333 字节，完整内容和摘要都已核对。小码据此增量修正，保留原件和作者记录，再交给独立测试与复核。最终小检的 HTTP 7 项、建设任务可信后端浏览器 30 项、静态浏览器 25 项分别通过，覆盖了双页面、失败重试、真实到期和输入保留等路径。

这个例子说明两件事。第一，测试要覆盖用户实际走的路径，不能用一份另外拼好的请求代替页面。第二，协作流程要能够接住交付后的纠错。完成一份首稿以后，新的证据还应该推动下一轮工作，而不是只能重新开一个孤立任务。

回到 02 两条案例，指 v6 结果区，需要原件时打开 最终交付。小检与建设任务的检查分别记载；v4 的 HTTP 10 项、后端 23 项、静态 19 项，以及 v5 静态 20 项，仍属于各自历史版本。

7:00–9:00｜看系统图：哪一部分是谁做的

点击 05 系统架构，放大运行图；随后点 07 五角色流程。按 Octo 输入→Steward→角色→GitHub→回报的顺序指图。

看过例子后，再看架构就容易理解了。左边的 Octo 是用户提出问题的地方。消息进入运行中的 OpenClaw 后，Steward 记录可信的来源和当前任务，按职责安排 Agent。

小丘负责问答、澄清和反馈入口；小助整理需求；小衡独立评审；小码开发演示；小检执行独立测试。GitHub 保存需求、评审、代码和报告。最后由既定的消息出口把结果送回原会话。

这里有两类资料。源码和知识帮助 Agent 判断产品事实；数据库记录这件事做到哪一步、有没有等待中的运行、哪些通知还没确认。把这两类信息分开，才不会把聊天里的“我做完了”误当作实际工作状态。

当前我们用一个 Gateway、一个业务插件和一份业务数据库承载主路径。Worker 是插件里的调度程序，不是另一位模型领导者。它按照已记录的阶段派任务，五个 Bot 不需要在群里互相接话才能继续工作。

停在 07 五角色流程 的分支处，说明普通问答可以直接结束；Bug 和 Feature 按各自流程处理，并非每条消息都进入开发。

9:00–11:00｜门控究竟强制了什么

点击 08 程序门控，再点 09 来源与回执。先讲一个关口，再讲来源与回执，不逐个念检查项。

我们没有规定 Agent 查第一个文件之后只能查第二个文件。它可以多轮搜索，发现信息不够后继续读取，也可以根据证据改变判断。

程序检查的是工作交接的前提。例如，建单需要真实来源和有效查重依据；需求就绪需要对应版本的独立评审；演示交付要绑定已经测试的候选；消息完成要有实际回执。前提缺失时，程序不会把它推进成完成状态。

再看来源。群里可能有两个人交错发消息，后台任务可能过几分钟才结束。此时不能看“最近一句是谁说的”决定回给谁。Steward 把原消息、提出者、位置和任务关联起来，后续仍沿原来源回去。

如果一次外部请求超时，也不能马上再发一遍。远端可能已经完成，只是返回结果丢了。程序要先核对原操作，再决定是否继续。这样才能降低重复建单和重复回报的风险。

这些检查能约束角色、版本和外部动作。它们不能替代内容判断，所以我们仍需要独立评审，也需要刚才看到的浏览器复验。

11:00–12:30｜谁能找哪位 Agent，能让它做什么

点击 10 身份与资源。先指参与者矩阵，再指只读资料、可写产物与外部目标。

普通用户可以找小丘问产品问题、提交反馈和查状态。配置中的负责人、观察者，以及明确放行的外部测试 Bot，可以向其他角色提出职责范围内的任务。未放行的 Bot 不会因为在群里发了一句话就得到团队响应。

小测能够参与测试，依据的是配置中的真实身份。它与小码、小检分开，避免让同一角色既提供测试输入，又开发、测试并证明自己的结果。

准入也只是第一层。即使允许提出任务，仍要遵守角色、阶段和资源边界；它不能随意更换目标仓库、读取凭证或跳过独立检查。普通用户的反馈可以进入预先授权的固定流程，但普通用户不能直接指挥开发或审批角色。

资料方面，Agent 可以读取需要的源码和共同知识；产物写入指定位置；凭证和运行配置留在它们不应接触的管理范围。权限是否可用、是否越界，要以实际工具与环境检查为准。

12:30–14:00｜知识库为什么需要版本与重新取证

点击 11 知识版本，指源码变化、知识待审和任务版本的不同位置。

知识库帮助 Agent 找到资料，但源码会变化。如果只刷新文档日期，旧结论并不会因此变成新结论。

我们让一次任务使用一致的源码版本，并记录它绑定哪份知识。发现上游变化后，相关知识进入待审，由作者和独立评审重新调查，再整体发布。旧任务继续保留自己的依据，新任务读取适合它的版本，避免把不同时间的材料混在一起。

还有一个容易误解的地方：引用可以打开，回答仍可能有错。某段代码是真实的，但结论可能漏掉配置条件、调用方或例外。程序可以检查路径、行号和版本，却不能单靠这些信息判断概括是否充分。

因此我们把引用检查和内容复核分开记录。遇到“这台实例现在有没有开启某项功能”，还要找部署和运行证据，不能把主分支里的实现直接说成实例现状。

14:00–15:30｜为什么要做静默扫描、缓存和恢复

点击 12 自动扫描，再点 13 缓存与恢复。只解释一条无变化路径、一条限流路径。

真实工作还需要在没人提醒时继续。Steward 定期检查需求池和资料是否发生变化。有新的需求或意见时，再安排模型理解和处理；没有变化也留执行记录，但不在群里反复播报“一切正常”。

缓存优化解决的是重复读取。多次查询同一份已验证资料，可以短期共享结果；评论没有变化时，可以避免重复传输正文。但缓存缺失或不完整，就要重新读取，关键写入之前也要核验依据。

页面中的请求数对比来自固定合成场景，只能说明那组条件下发生了什么，不能说成线上整体节省比例。304 也仍然是一次 HTTP 请求。

遇到限流时，程序保存待办并按服务端要求等待；遇到写入结果不确定时，先查远端是否已经完成。没有有效查重依据的反馈，仍要取得新的查询和判断，不能把“网络恢复了”当作“可以盲目建单”。

15:30–17:00｜为什么经历三次工程选择

点击 03 工程选择。若听众关心参考来源，再短暂点 04 历史资产，只说方法，不展开私有资料。

我们不是一开始就做成现在的结构。V1 已经有真实协作、Hook 和脚本，也吸收了既有知识工程、ATE 和 Meta_Kim 的方法。它的问题是规则分散在多个地方，角色文档、定时提示和运行配置越来越难保持一致。

V2 把身份、事件、权限和恢复设计得更完整，也做出了实质代码。但需要接通的适配器和运行边界更多，一些角色声明了能力，实际工具和环境还没有准备好。设计范围与真实业务接通速度开始脱节。

用户随后选择收敛到 MVP。我们先完成三角色的支持与需求闭环，再按实际演示交付需要增加开发和独立测试。扩成五角色以后，仍沿用同一个插件、业务库和来源机制。

所以比较版本时，要同时看解决了什么、实际接通了什么，以及维护成本。不能按 Agent 数量判断谁更好，也不能把先前版本的有效成果一笔抹掉。

17:00–18:30｜未知怎么处理，安全结果怎么讲

点击 14 人工协作，再点 16 安全修复；只有被问到连续测试时再切 15 连续安全验证。不要展示私密攻击日志。

当资料不足时，小丘要说明不知道哪部分、需要补什么证据，以及应向谁求助。负责人从配置中确定，通知仍按原会话规则处理。求助已经发出，只能说明通知的状态，不能说人已经接手或问题已经解决。

安全也需要按实际运行位置分开看。Agent 的命令在容器里执行，宿主插件还要安全地收集文件和发布内容；生成的 JavaScript 到了用户浏览器，又有另一套执行边界。验证一个位置，并不自动证明另外两个位置安全。

本轮防护修复已经安装，六个旧预览已经迁移，公开文件读回全部匹配。当前 #9 第二版和 #10 第六版也完成了各自的演示验收。原始代码和历史署名保留，新的受限预览有独立入口。

真实凭证相关测试初段发送了 14 条，检查了 13 条输出，随后按平台要求停止，原定 20 多条目标没有完成。后续 12 条合成和 5 条普通群控制另外记账。还有五次 Bot 私聊在发送前被好友门禁拦住，没有发生 Agent 运行。已核对的结果都有覆盖范围，不能合并成一句“安全和私聊全部通过”。

18:30–20:00｜用可核对的结果收尾

点击 18 完成边界，最后点 21 证据入口。在页面上指出 #9 打回、#10 浏览器反馈和最终交付三个入口，留时间让听众看链接。

回到今天最初的问题：这支团队能否把一件事继续办下去？两个案例提供了具体证据。从独立输入、新事项、需求修订，到开发、独立测试、复核和回报，相关角色、版本和产物都可以追查。

20 / 术语与常见追问

把术语翻译成可以使用的理解

第一次讲解不需要记住所有实现名。先知道每个概念回答什么问题，再按需要看技术说明。

讲者辅助 先说人话，再按需要展开技术

遇到术语先翻译成它回答的问题：是谁、做到哪里、依据哪版、是否实际发生。能说清这四件事，就能理解大部分设计。

怎么展开这一章不必逐条讲完术语表，把它作为现场追问的备用解释。

这句话要说准不清楚的地方说当前证据和待核实范围，不补造实现。

Agent / Bot

Agent 是带职责和工具的执行者；Bot 是它在聊天平台中的账号身份。一个运行身份和一个聊天身份需要准确绑定。

Gateway / Plugin / Worker

Gateway 提供运行基础；插件接入业务能力；Worker 是插件中定时检查和派发任务的程序。

Skill / Hook / 状态机

Skill 教方法；Hook 在执行节点接入检查；状态机记录当前阶段及允许的下一步。三者可以共同工作。

来源 / 版本 / 回执

来源回答“谁、在哪里提出”；版本回答“依据哪一份”；回执回答“外部是否实际发生”。

幂等 / 对账

幂等避免同一件事重复产生效果；对账是在结果不确定时先核对远端，而不是再做一次。

快照 / 哈希 / 独立审核

快照固定读取版本；哈希检查内容是否变化；独立审核判断内容是否被证据支持。三者不是同一件事。

缓存 / 304 / 限流

缓存复用已验证资料；304 表示无需重传正文；限流要求按服务端节奏等待。304 仍是一次请求。

沙箱 / 最小权限

沙箱限制代码能触达的环境；最小权限让任务获得必要资源，又不能顺便访问凭证或其他数据。都要实际验证。

Steward 究竟是一个机器人，还是一个软件？

Steward 是我们编写的软件插件，运行在 OpenClaw 中。它管理事项阶段、角色交接、来源和外部回执。小丘、小助等 Agent 才是负责理解、调查和产出的执行者；Bot 是它们在 Octo 上的聊天账号。这样分开以后，就不会把一个聊天账号当作全部系统。

展开位置：01 项目定义、05 系统架构。

用一个很强的模型把事情做完，不是更简单吗？

简单任务可以由一位 Agent 完成。这里把作者与评审、开发与测试分开，是为了让另一位角色重新核对背景和产物。#9 的独立评审实际纠正了作者的范围决定，所以这次分工有证据支持。增加角色也会增加成本，我们没有把角色越多当作目标。

展开位置：02 两条案例、07 五角色流程。

程序强制流程以后，Agent 还有自主性吗？

有。Agent 可以选择调查路径、多次搜索和续读、比较资料，也可以改变自己的结论。程序检查的是阶段之间的条件，例如真实来源、当前版本、独立评审和送达依据。它不会规定所有问题都读同一批文件，也不会让普通问答强制走完开发流程。

展开位置：08 程序门控。

门控能不能保证 AI 的答案正确？

不能保证内容一定正确。程序可以发现角色不符、版本过期、引用没有依据或缺少必要评审；结论是否充分、需求是否合理，仍要靠调查和内容复核。#10 的 HTTP 测试已经通过，浏览器仍然发现问题，就是为什么我们还要做实际操作验证。

展开位置：08 程序门控、02 两条案例、11 知识版本。

Skill、Hook 和程序门控有什么区别？

Skill 主要说明完成任务的方法。Hook 是在运行节点接入处理逻辑的入口，它既可以补充上下文，也可以在执行前检查并拒绝。门控说明满足什么条件才能继续，还需要状态记录和最终执行层共同配合。V1 已经有真实 Hook，MVP 的变化是把更多必要检查接到同一条业务路径中。

展开位置：08 程序门控、03 工程选择。

独立评审一定要使用不同模型吗？

本项目的独立首先指角色、任务、会话和检查职责分开，评审者重新读取背景并核对具体版本，并不要求换底座模型。相同模型仍可能有共同偏差，所以两个角色都说通过也不是最终真理。还要看具体理由、独立测试和实际使用结果。

展开位置：07 五角色流程、02 两条案例。

#9 没讨论过批量管理，为什么不能直接说本期不做？

因为“尚未讨论”和“已经决定排除”是两种状态。作者可以把它列为待确认问题，也可以说明当前演示覆盖到哪里，但不能假装用户已经作出范围决定。转成开放问题也不表示一定要开发批量能力，仍需后续确认。

证据：首次打回、PRD v2。

PRD 只写 What、不写 How，具体是什么意思？

需求文档先写用户要得到什么结果，以及怎样判断结果成立。例如到期以后取消置顶、原消息保留、保存失败时保持原状态。使用哪张表、哪种缓存属于实现选择，应由后续开发讨论。这样评审能先检查需求本身，不会被一份看起来很技术化的方案掩盖范围问题。

展开位置：02 两条案例、07 五角色流程。

小测被放行以后，是不是想让团队做什么都可以？

不是。配置放行让这个真实身份进入职责范围内的任务入口，它仍不能更换外部目标、读取凭证或跳过评审和测试。小测只提供测试输入，不兼任开发或独立测试者。普通真人可以通过小丘问答、反馈和查状态，不能直接指挥其他执行或审批角色。

展开位置：10 身份与资源。

普通人不能找小码，是不是他的需求也不会被开发？

不是。普通人的反馈可以由小丘澄清、查重并登记，再进入已经配置授权的固定流程。限制的是直接调度其他角色、扩大权限或跳过阶段；它不妨碍一条有效反馈最终形成经过评审的需求和后续工作。

展开位置：10 身份与资源、07 五角色流程。

为什么不能直接在群里写“@某人”作为身份依据？

名字和文本可以被复制，也可能重名。平台的原生提及带有实际账号标识，程序要按这些结构化信息判断消息写给谁，再按保存的原消息来源回复。用户看到的是自然的提及和引用，后台不能只拿这几个字猜测身份。

展开位置：09 来源与回执。

引用链接可以打开，为什么还要复核回答？

链接能证明这段资料存在，却未必能支持整个结论。Agent 可能只看了一个函数，漏掉调用条件或其他分支。我们需要核对本轮读取、版本和引用范围，再判断这些证据是否足够。涉及实例现状时，还要另外查部署和运行记录。

展开位置：11 知识版本。

源码更新以后，旧任务和旧知识怎么办？

旧任务保留它已经绑定的版本，便于解释当时的判断；新任务按新的可用版本取证。发现源码变化后，知识进入待审，重新调查和独立审核后再发布。不能把不同版本的片段拼起来，也不能只改文档日期就说知识已经更新。

展开位置：11 知识版本。

为什么不让 AI 每隔几秒主动看看有没有新任务？

是否到检查时间、目录和评论有没有变化，这些适合由程序处理。发现确实需要理解或写作的内容时，再调用模型。这样既有持续执行记录，也能减少无必要的模型工作。页面上的定时机制和模型调用是两层，不能把每次本地检查都算成一次网络请求或模型调用。

展开位置：12 自动扫描、13 缓存与恢复。

缓存会不会让系统漏掉早期评论的修改？

这正是检查范围需要明确的原因。当前扫描按页检查目录和评论，条件请求只有在缓存完整且匹配时才能复用。不能仅凭 Issue 更新时间没变就跳过评论，也不能把缺页或网络失败记成没有变化。关键操作前还要重新核验依据。

展开位置：13 缓存与恢复。

为什么超时后不直接重试一次？

要先分清超时发生在哪一步。如果远端已经创建事项，只是回执丢了，再发一次就可能重复建单。程序应保存原操作身份，去远端核对后再继续。尚未执行的待办可以等待恢复；缺少有效查重依据的任务，则需要新的查询和判断。

展开位置：09 来源与回执、13 缓存与恢复。

Issue 还开着，能说项目完成了吗？

要说明完成到哪一层。当前两条案例完成了需求评审和可运行演示，并有对应测试与回报；它们没有因此进入真实 Octo 生产环境。PRD ready、演示验收、代码合并和生产发布各有条件。保留 Issue 打开，正是在避免把演示完成误写成功能上线。

展开位置：18 完成边界。

HTTP 测试和浏览器测试到底差在哪里？

HTTP 测试直接请求后台，检查权限、数据和错误处理。浏览器测试从按钮和输入框走用户路径。#10 第四版只有放慢输入才发现刷新覆盖草稿；第五版静态检查通过，后端页面却因请求头不符合预览桥协议而失败。这说明还要分清版本、操作速度和运行模式。第六版的独立 HTTP 7 项、可信后端浏览器 30 项、静态浏览器 25 项分别通过，旧版失败与统计仍保留。

证据：v2 浏览器反馈、v3 一致性反馈、v6 最终交付。

转人工是不是意味着系统只能停在那里？

某个阶段缺少关键事实或决定时，要明确留下缺口并找配置负责人。其他可以调查、恢复或处理的工作仍按各自状态继续。求助通知发出后，不能假设人已经接手；当前并没有用这条通知冒充完整的人工接手工单流程。

展开位置：14 人工协作。

有 Docker 以后，为什么还要管宿主文件和浏览器？

因为代码会在不同位置执行。Docker 限制 Agent 的命令环境；宿主插件还会收集产物并发布，必须自己检查路径与内容；生成的 JavaScript 到了用户浏览器，又需要浏览器层面的限制。一个位置的检查通过，不能替另外两个位置作证明。
