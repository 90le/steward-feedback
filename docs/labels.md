# 标签与状态

GitHub 的 `open` / `closed` 表示 Issue 是否打开；`status/…` 标签表示需求处理阶段。两者需要一起看，并结合最新评论、PRD 与评审记录判断。

## 类型与优先级

| 标签 | 含义 |
| --- | --- |
| `type/bug` | 已有行为异常或缺陷反馈。 |
| `type/feature` | 新能力或体验改进需求。 |
| `priority/p1` | 紧急或阻断。请说明受阻任务与影响。 |
| `priority/p2` | 正常优先级，也是新表单和收单的默认值。 |
| `priority/p3` | 较低优先级。 |

优先级用于讨论处理顺序，不代表响应时限、排期或上线承诺。影响不明确时可先用默认 `p2`，再补充事实供维护者判断。

## 业务状态

| 标签 | 含义与下一步 |
| --- | --- |
| `status/triage` | 待分类或初步梳理，确认问题类型与必要信息。 |
| `status/needs-info` | 需要补充信息或澄清分歧。根据最新评论回答具体问题；也可能出现在 PRD 修订之后。 |
| `status/prd-drafting` | 正在起草 PRD，尚无独立评审通过结论。 |
| `status/prd-review` | PRD 进入独立评审，查看待评审版本及评论。 |
| `status/prd-revise` | PRD 需要修订，作者应逐项回应评审意见或新增诉求。 |
| `status/prd-ready` | 具体 PRD 版本已通过独立评审，需求文档就绪。 |

功能需求的预期路径为：待分类 → 起草 → 独立评审 → 按需修订和再次评审 → PRD 就绪。缺少信息时先澄清。Bug 不默认经过这条 PRD 路径。

**`status/prd-ready` 不代表需求已开发、Bug 已修复或软件已发布，也不要求关闭 Issue。** 后续新诉求不自动获得旧版本的评审结论。

## 打开、关闭与关闭原因

| GitHub 记录 | 应如何理解 |
| --- | --- |
| `open` | 事项仍打开；继续结合业务标签和最新产物查看进度。 |
| `closed`，原因为 `completed` | 维护者按“完成”关闭。是否已实现、修复或发布，仍需查具体说明与相关证据。 |
| `closed`，原因为 `not_planned` | 按“不计划处理”关闭；具体理由以关闭说明为准。 |
| 标为重复，如 `duplicate` 标签或重复事项说明 | 查看指向的原 Issue，并在那里继续跟踪。重复标签本身不等于已关闭或已修复。 |
| `closed`，缺少明确原因 | 只能确认已关闭，不推断处理结果。 |
| 重新打开 | 回到打开状态，不表示此前问题已解决；查看重新打开的说明。 |

若维护者写明“未复现”“不再需要”等原因，按该记录理解。单凭标签、关闭图标或聊天中的“完成”不能推断软件交付状态。

## 兼容其他标签

当前处理逻辑兼容普通 `feature` 和 `bug` 标签；新表单使用 `type/feature` 和 `type/bug`，不要求提交者另建旧写法标签。

上述 11 个标签分属类型、优先级和业务状态三个维度。调整一个维度时，应保留其他维度及不冲突的附加标签。普通附加标签可用于描述主题，不能仅凭标签名称推断它会触发自动流程。

同一维度通常保留一个明确值；若出现冲突、缺失或标签与评论不一致，请在原 Issue 请求核对。本文解释标签含义，不证明自动分类、流转或通知已经执行。
