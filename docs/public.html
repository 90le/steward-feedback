01 / 产品定位

Steward 是带着 AI 团队办事的流程程序

它记录事情做到哪一步、下一步交给谁、还缺什么条件，以及结果是否已经发生。

在产品群里，一个问题可能需要查源码，一条建议可能需要整理成需求，一份演示还需要有人检查。把这些工作交给多个 AI 之后，团队仍然要知道：谁提出了问题、哪一版需求已经确认、哪些意见尚未处理、测试的是哪份代码，最后应该向谁回报。

Steward 把这些信息保存在同一条工作记录中。五位 Agent 分别负责理解、调查、写作、评审、开发与测试；程序依据实际状态安排下一步。用户可以持续补充同一事项，后续角色也能沿原有版本和证据继续工作。

运行基础

OpenClaw

运行 Agent，提供模型、会话、工具调用和沙箱能力。

业务组织

Steward

作为 OpenClaw 中的业务插件，管理来源、阶段、版本、任务与外部结果。

具体执行

五位 Agent

在各自职责内多轮查资料、比较证据、形成判断并完成产物。

阶段内自主调查，阶段之间检查条件。

Agent 可以根据新证据改变判断。建单、需求就绪、演示发布等关键步骤，需要满足程序定义的前提，再继续推进。

当前产品聚焦 Octo 的支持、反馈与需求协作，并把通过评审的新功能需求延伸到可运行演示。演示可以包含前端与后端；正式 Octo 功能的集成、合并和生产发布仍需另行完成。

02 / 使用场景

从产品问答，延伸到需求与演示交付

不同的问题走不同路径。小丘先理解你要办的事，再选择答复、澄清、登记或跟进。

查清产品行为

“这个功能支持什么？为什么这个操作会被拒绝？”

小丘调查产品资料与源码，核对相关条件和调用路径，再解释结论及依据。遇到版本不明或缺少实例信息的问题，会说明已知范围和需要补充的内容。

收集产品缺陷

“我点了这个按钮，实际结果和预期不一样。”

小丘询问复现步骤、实际现象和预期结果，检查是否已有相同记录，再登记或关联事项。Bug 默认进入问题跟踪流程，后续状态变化可以回报给提出者。

把建议整理为可执行的需求

“我希望增加一种更方便的处理方式。”

团队先确认使用场景、目标和范围，再起草需求说明书，交给独立角色评审。对于未讨论的选择，保留待确认问题；用户的实质补充可以推动后续版本。

体验演示并继续改进

“流程看起来合理，实际操作时还有一个问题。”

已启用的演示流程会接续开发、独立测试和交付复核。你可以体验公开预览，将新的发现补充到原事项，团队依据新的需求版本继续修订。

Steward 适合希望把产品支持与反馈处理连起来的团队：使用者通过一个入口沟通，产品、开发和维护人员可以查看结构一致的记录，判断当前进度和下一步需要谁参与。

03 / 开始使用

先找小丘，描述你的场景

在已经接入 Steward 的 Octo 会话中提出问题，也可以通过公开需求池提交或补充事项。

一条具体的需求示例
“活动结束后，通知还一直置顶。我希望能设一个到期时间，自动取消置顶，但保留原消息。”

这条描述提供了使用场景、期望变化和保留条件。你不需要先掌握代码或写完整需求文档。

  1. 说清遇到了什么产品问答给出功能或操作背景；反馈 Bug 补充复现步骤、实际现象与预期结果。
  2. 回答必要的澄清范围不清楚时，小丘会继续追问。已有相似事项时，可以关联已有记录一起跟踪。
  3. 沿原事项查看后续保留事项编号，在原会话或 Issue 中补充信息、查看进展和反馈演示问题。
入口怎样使用你能得到什么
Octo 已接入群用自然语言向小丘提出产品问题或反馈。小丘无需被 @，但只参与相关问题和必要追问。答复、澄清、事项记录和后续回报。
已具备访问条件的私聊从自己的会话与小丘沟通；仍需满足平台与项目的访问条件。沿原用户会话处理，不把私聊内容转入群中。
GitHub 需求池先查看已有事项，再通过表单提交 Bug 或 Feature，或在原事项中补充。公开、可持续追踪的正文、讨论、版本与产物记录。

普通参与者可以通过小丘问答、反馈和查状态。直接向其他角色分派任务属于另一种权限，由项目配置限定。群内闲聊、明确写给其他人的消息，以及未放行 Bot 的输入不会触发整支团队。

04 / 角色分工

五个角色，各自承担明确责任

作者、评审者和测试者分别工作。每一轮产物保留对应角色和版本，方便追查修改与检查结果。

支持入口

Octo 小丘

理解问题，调查依据，接住后续

处理产品问答、相关性判断、反馈澄清、语义查重和正式收单；解释事项状态，汇总真实结果与需要人工处理的缺口，并保留提出者与原会话的关联。

需求作者

Octo 小助

写清目标、范围和验收标准

起草与修订 PRD，也承担知识候选的重新调查。需求文档重点描述用户要实现什么、哪些内容属于范围、怎样判断做对了；根据具体评审意见修改，不批准自己的稿件。

独立评审

Octo 小衡

对照诉求和证据，检查当前版本

独立评审 PRD、知识内容与演示交付。检查内容是否回应原始目标、是否漏掉条件或引入未确认假设，并给出能够执行的修订意见。

演示开发

Octo 小码

把已经评审的需求做成可运行演示

编写演示前端、后端和启动说明，提交代码与候选产物。后续修订可以基于上一版代码增量修改，同时保留历史原件、版本和作者记录。

独立测试

Octo 小检

编写测试并实际执行

检查候选产物，提供可复跑的测试脚本、结果和问题说明。后台程序再对冻结的候选复跑检查，交付前由小衡综合需求与测试证据复核。

后台 Worker 是 Steward 的调度程序，负责按记录派发工作。五个 Bot 通过程序交接，用户无需在每个阶段分别提醒。公开产物中的统一发布账号也不代替实际作者、测试者和评审者的署名。

05 / 协作流程

一条新需求，怎样从反馈走到演示

下面展示新功能的主要路径。澄清、修订、等待和人工求助都是流程中的正常状态。

  1. 理解与查重

    小丘确认使用场景，查询已有的开放和已关闭事项，比较语义、对象与差异。信息不足时先澄清；已有同类事项时建立关联；具备有效查重依据后再正式登记。

  2. 起草需求说明

    小助将诉求整理为 PRD，写明用户目标、范围与用户能感知的验收条件。尚未讨论的选择保持待确认，避免把作者的假设变成用户已经认可的决定。

  3. 独立评审与修订

    小衡对照原始诉求检查当前版本。初稿未通过时，小助根据意见进行自动修订；仍有关键分歧时，团队提出具体待决问题。之后新增的实质信息可以开启新版本。

  4. 接续演示开发

    需求通过独立评审后，已启用的流程根据版本与状态安排小码开发。程序记录代码、启动说明和候选内容，避免把同一版本重复安排为新任务。

  5. 测试与交付复核

    小检独立编写并执行测试。程序将检查结果绑定到这份候选，小衡再核对需求、产物和证据。发现问题就进入修订；超出自动修订范围时保留缺口并求助。

  6. 发布演示并回报

    交付包含代码、预览入口、说明和测试记录。程序核对外部产物及发送结果，再沿原会话回报。用户后续的补充继续留在同一事项中。

问答、Bug 和 Feature 各有自己的处理路径。

普通源码问答可以在充分调查后直接答复；Bug 默认登记并跟踪；Feature 进入需求流程。PRD 就绪或演示发布，都不会自动变成“正式功能已经上线”。

06 / 真实交付案例

从需求变化与实际结果，看团队如何工作

两条案例均在受控联调中经过真实 Octo、OpenClaw 和 GitHub 链路，完成角色协作、产物交付与回报。公开预览使用模拟数据。

案例 #9 · PRD v2

群置顶消息，到期后自动取消置顶

用户希望解决的问题

临时资料或活动通知已经过期，却仍占据群置顶列表，需要有人回来清理。用户希望设定一个未来时间，到期后自动取消置顶，同时保留原消息，避免影响其他置顶内容。

需求如何得到澄清与修订

小丘先确认“取消置顶”与“删除消息”的区别，再查重、登记。小助的首稿曾把“批量到期管理”列为非目标；小衡发现用户尚未讨论这一选择，要求撤下未经确认的排除。第二版将其改为开放问题，随后通过独立复审。

首稿直接排除批量设置

作者替用户补了一项未确认的范围决定。

评审保留用户的决定空间

没有讨论过的内容，需要确认后再确定范围。

第二版改为待确认问题

完成修订后，再进入开发、测试和交付复核。

演示中可以体验什么

  • 为临时置顶设定未来的到期时间。
  • 实际等待到期后，看到它退出置顶列表。
  • 确认原消息与其他永久置顶仍然保留，不额外发送一条到期通知。

本案例保留独立接口测试、后端模式与静态预览的操作结果。团队交付的是这份可运行演示；对应 Issue 仍保持打开，正式 Octo 功能尚未发布。

案例 #10 · PRD v6

个人提及提醒，支持“稍后处理”

用户希望解决的问题

用户暂时忙，希望自己的提及提醒晚一点再出现。延后只影响本人，不改变原群消息和他人的提醒。讨论进一步明确：查看原消息后，延后安排继续有效；明确标记已经处理，才取消后续提醒。

为什么经历多轮修订

早期版本已有独立接口测试，但浏览器操作发现，页面上的默认时间会被后台拒绝，“查看原消息”也只给出提示，没有展示原文。随后复测又发现跨页状态不同步，以及定时刷新覆盖正在编辑的时间。用户实际经过的路径，为团队提供了新的修订依据。

实际发现的问题后续修订
默认的稍后时间失败，原文入口没有显示内容统一时间约定，实际显示并定位模拟原文；区分“查看”和“已处理”。
另一页处理完成，本页刷新仍显示未处理修正跨页与重载后的状态展示，读取已经保存的结果。
慢慢编辑日期时，刷新把输入覆盖保留编辑草稿，允许错误后直接修正和重试。
后端联调请求不兼容，短时选项生成过去时间第六版沿用上一版代码增量修正，核对后端与静态模式。

当前版本与验证结果

反馈持续回到同一个 Issue，经需求修订、开发、独立测试与复核，形成第六版。小检提供了独立接口测试，建设过程另外完成后端模式和静态预览的操作检查，涵盖到期、重试、双页面状态和编辑保持等场景。不同检查者和历史版本的记录分别保留。

你可以在预览中推迟提醒、查看原文、标记已处理，并观察状态变化。案例表明交付后的问题可以继续进入原流程修订，也说明接口测试与实际页面操作需要相互补充。

07 / 系统组成

沟通、AI 工作、业务记录和产物各有位置

Steward 运行在 OpenClaw 中，连接 Octo 会话与 GitHub 需求池。业务数据库保存任务进度，源码与知识提供调查依据。

组成部分负责什么保存或产生的内容
Octo接收问题、补充信息、提出必要澄清并回报结果。原会话、原消息及提出者的可信关联。
OpenClaw Gateway运行 Agent 会话，提供模型、工具与沙箱能力。各角色的实际运行和工具执行结果。
Steward 插件与 Worker检查身份、来源、阶段与版本；派发任务，管理外部动作和恢复。工作交接、待办、产物状态和发送回执。
业务数据库持续记录消息、任务、意图、重试和通知结果。可在重启后继续核对与处理的工作状态。
源码与知识支持事实调查，提供固定版本的产品材料和经验。只读快照、已发布知识及任务绑定的依据。
GitHub 需求池保存正式事项、需求、评审、演示代码与测试报告。参与者可查看、讨论和追溯的项目产物。

业务记录与知识资料分开维护：前者回答“这件事做到哪一步”，后者支持“产品事实是什么”。Agent 结束一次运行后，程序还会检查相应外部效果；创建事项、发布需求、交付演示和送达通知各有自己的结果记录。

08 / 交接与质量

关键条件满足后，工作才进入下一阶段

Steward 将角色、版本与完成条件落实到程序检查中，同时保留模型调查与独立质量判断。

建单前

有效查重依据

确认查询已完成、候选真实存在，且本轮判断仍然适用。缺少依据时保存待办，继续核对。

需求就绪前

独立评审当前版本

作者提交后，由对应评审角色检查本版内容。未通过则修订，或提出具体待决问题。

演示交付前

实际测试与复核

测试脚本、执行结果与冻结候选一致，并由独立角色复核需求和产物。

确认送达前

真实外部回执

确认产物或消息已经在原目标中出现。结果不确定时，先核对原操作，再决定怎样继续。

这些检查约束“谁可以做、依据哪一版、前提是否齐全”。内容是否切题、需求是否合理、测试是否充分，仍需要 Agent 调查、独立评审和实际使用验证。

判断对象需要内容判断的部分程序核对的部分
两条反馈是否重复比较场景、对象和差异，必要时向用户澄清。查询完整性、候选依据与有效时间。
需求是否回应原诉求目标、范围、验收标准与未确认假设。作者与评审角色、对应版本和修订记录。
演示是否可用实际交互和测试覆盖能否支持结论。脚本是否执行、候选是否一致、发布前提是否满足。

知识、技能和角色要求帮助 Agent 完成当前工作；阶段记录与执行检查负责控制交接。模型说“完成了”之后，还需要相应产物和真实结果来支持这一状态。

09 / 知识与依据

让答复对应真实材料与明确版本

小丘可以多轮检索、读取、续读与比较。知识帮助定位，具体结论还要依据本轮实际调查。

当前知识覆盖九个产品与工程领域，帮助角色找到相关资料，理解模块关系、配置条件和常见判断方法。用户不需要掌握这些分类，仍然可以用日常语言提问。

D1

认证与身份

用户、Bot 与连接怎样证明身份。

D2

权限模型

组织、频道与角色允许执行哪些动作。

D3

配置与启动

配置怎样读取，运行前需要满足什么。

D4

业务模块

各模块负责什么，在哪里注册与启用。

D5

接口与错误

请求、响应、错误码及调用链的条件。

D6

即时通信

消息控制服务与通信基础设施怎样分工。

D7

Bot 与 Agent

注册、配置、身份与会话启动方式。

D8

存储与依赖

数据库、缓存和对象存储用于哪些环节。

D9

构建与发布

代码怎样构建，与容器及部署项目怎样关联。

答复怎样给出依据

涉及源码的结论会附路径、行号和固定提交链接，说明依据哪个版本。程序核对引用与实际读取记录；回答还需要解释该条件为什么支持结论。一次检索没有找到结果时，角色应继续判断是否查全，而不能据此断言产品没有相应能力。

源码问答示例

“App Bot 能否向群发送消息？”

11 / 自动跟进

没有人提醒时，按真实变化继续工作

Worker 定期检查源码与 GitHub 事项。当前既定检查周期为 120 秒；网络等待与服务限流可能影响实际发现时间。

发现什么接下来怎样处理
新的 Feature 或新增功能标签读取背景，根据已有任务与内容进入适当的需求阶段。
正文或评论出现实质补充比较新的输入，必要时起草或修订对应版本的需求。
新的 PRD 通过独立评审根据已启用策略、产物与版本状态接续演示开发。
事项关闭、重开或关闭原因变化向相关的原订阅来源回报实际状态与说明。
源码发生变化核对新版本是否可读，安排知识待审和重新调查。
完整检查后没有变化记录本轮扫描，不调用模型、不重写需求，也不向群里例行播报。

怎样减少重复工作

程序根据事项、版本和产物记录安排任务，避免把同一份就绪需求重复当作新工作。读取外部资料时，可以复用短期内已经验证的完整内容；相同的读取请求也可以共享结果。关键写入前仍要检查依据是否有效。

评论分页不完整、请求失败或内容尚未核对时，会保留不完整状态，不把它登记为“没有变化”。这既影响后续安排，也影响能否形成有效的查重判断。

遇到网络失败或限流怎么办

服务要求等待保存待办，按要求恢复

保留原业务意图和来源，等待后重新核验判断。无法完成查重的反馈，仍需取得有效依据后才能建单。

写入结果不确定先查询原操作的结果

远端可能已经完成，只是响应丢失。程序先核对是否已经创建或发送，再决定怎样继续，降低重复写入的风险。

业务数据库持续保存待办、等待与回执状态。重启后，程序可以继续核对这些记录；实际服务不可用时，待办仍需等待恢复，不能把等待状态报告为完成。

常见状态怎样理解

你看到的状态实际含义你可以怎样配合

通知持续失败或长时间等待时，程序记录阻塞并进行定向告警，避免跨重启重复通知。确认平台侧送达只说明消息已经发送；人工是否已读、已接手或已经解决，需要另外的实际结果。目前还没有完整的人工接手工单生命周期。

15 / 术语与常见追问

术语与常见追问（Q&A）

从基础概念到实际使用、质量检查和完成范围，下面保留完整的 24 组问答。

Agent / Bot

Agent 是带职责和工具的执行者；Bot 是它在聊天平台中的账号身份。一个运行身份和一个聊天身份需要准确绑定。

Gateway / Plugin / Worker

Gateway 提供运行基础；插件接入业务能力；Worker 是插件中定时检查和派发任务的程序。

Skill / Hook / 状态机

Skill 教方法；Hook 在执行节点接入检查；状态机记录当前阶段及允许的下一步。三者可以共同工作。

来源 / 版本 / 回执

来源回答“谁、在哪里提出”；版本回答“依据哪一份”；回执回答“外部是否实际发生”。

幂等 / 对账

幂等避免同一件事重复产生效果；对账是在结果不确定时先核对远端，而不是再做一次。

快照 / 哈希 / 独立审核

快照固定读取版本；哈希检查内容是否变化；独立审核判断内容是否被证据支持。三者不是同一件事。

缓存 / 304 / 限流

缓存复用已验证资料；304 表示无需重传正文；限流要求按服务端节奏等待。304 仍是一次请求。

沙箱 / 最小权限

沙箱限制代码能触达的环境；最小权限让任务获得必要资源，又不能顺便访问凭证或其他数据。都要实际验证。

Steward 究竟是一个机器人，还是一个软件？

Steward 是我们编写的软件插件，运行在 OpenClaw 中。它管理事项阶段、角色交接、来源和外部回执。小丘、小助等 Agent 才是负责理解、调查和产出的执行者；Bot 是它们在 Octo 上的聊天账号。这样分开以后，就不会把一个聊天账号当作全部系统。

用一个很强的模型把事情做完，不是更简单吗？

简单任务可以由一位 Agent 完成。这里把作者与评审、开发与测试分开，是为了让另一位角色重新核对背景和产物。#9 的独立评审实际纠正了作者的范围决定，所以这次分工有证据支持。增加角色也会增加成本，我们没有把角色越多当作目标。

程序强制流程以后，Agent 还有自主性吗？

有。Agent 可以选择调查路径、多次搜索和续读、比较资料，也可以改变自己的结论。程序检查的是阶段之间的条件，例如真实来源、当前版本、独立评审和送达依据。它不会规定所有问题都读同一批文件，也不会让普通问答强制走完开发流程。

门控能不能保证 AI 的答案正确？

不能保证内容一定正确。程序可以发现角色不符、版本过期、引用没有依据或缺少必要评审；结论是否充分、需求是否合理，仍要靠调查和内容复核。#10 的 HTTP 测试已经通过，浏览器仍然发现问题，就是为什么我们还要做实际操作验证。

Skill、Hook 和程序门控有什么区别？

Skill 主要说明完成任务的方法。Hook 是在运行节点接入处理逻辑的入口，它既可以补充上下文，也可以在执行前检查并拒绝。门控说明满足什么条件才能继续，还需要状态记录和最终执行层共同配合。V1 已经有真实 Hook，MVP 的变化是把更多必要检查接到同一条业务路径中。

独立评审一定要使用不同模型吗？

本项目的独立首先指角色、任务、会话和检查职责分开，评审者重新读取背景并核对具体版本，并不要求换底座模型。相同模型仍可能有共同偏差，所以两个角色都说通过也不是最终真理。还要看具体理由、独立测试和实际使用结果。

#9 没讨论过批量管理，为什么不能直接说本期不做？

因为“尚未讨论”和“已经决定排除”是两种状态。作者可以把它列为待确认问题，也可以说明当前演示覆盖到哪里，但不能假装用户已经作出范围决定。转成开放问题也不表示一定要开发批量能力，仍需后续确认。

证据：首次打回、PRD v2。

PRD 只写 What、不写 How，具体是什么意思？

需求文档先写用户要得到什么结果，以及怎样判断结果成立。例如到期以后取消置顶、原消息保留、保存失败时保持原状态。使用哪张表、哪种缓存属于实现选择，应由后续开发讨论。这样评审能先检查需求本身，不会被一份看起来很技术化的方案掩盖范围问题。

小测被放行以后，是不是想让团队做什么都可以？

不是。配置放行让这个真实身份进入职责范围内的任务入口，它仍不能更换外部目标、读取凭证或跳过评审和测试。小测只提供测试输入，不兼任开发或独立测试者。普通真人可以通过小丘问答、反馈和查状态，不能直接指挥其他执行或审批角色。

普通人不能找小码，是不是他的需求也不会被开发？

不是。普通人的反馈可以由小丘澄清、查重并登记，再进入已经配置授权的固定流程。限制的是直接调度其他角色、扩大权限或跳过阶段；它不妨碍一条有效反馈最终形成经过评审的需求和后续工作。

为什么不能直接在群里写“@某人”作为身份依据？

名字和文本可以被复制，也可能重名。平台的原生提及带有实际账号标识，程序要按这些结构化信息判断消息写给谁，再按保存的原消息来源回复。用户看到的是自然的提及和引用，后台不能只拿这几个字猜测身份。

引用链接可以打开，为什么还要复核回答？

链接能证明这段资料存在，却未必能支持整个结论。Agent 可能只看了一个函数，漏掉调用条件或其他分支。我们需要核对本轮读取、版本和引用范围，再判断这些证据是否足够。涉及实例现状时，还要另外查部署和运行记录。

源码更新以后，旧任务和旧知识怎么办？

旧任务保留它已经绑定的版本，便于解释当时的判断；新任务按新的可用版本取证。发现源码变化后，知识进入待审，重新调查和独立审核后再发布。不能把不同版本的片段拼起来，也不能只改文档日期就说知识已经更新。

为什么不让 AI 每隔几秒主动看看有没有新任务？

是否到检查时间、目录和评论有没有变化，这些适合由程序处理。发现确实需要理解或写作的内容时，再调用模型。这样既有持续执行记录，也能减少无必要的模型工作。页面上的定时机制和模型调用是两层，不能把每次本地检查都算成一次网络请求或模型调用。

缓存会不会让系统漏掉早期评论的修改？

这正是检查范围需要明确的原因。当前扫描按页检查目录和评论，条件请求只有在缓存完整且匹配时才能复用。不能仅凭 Issue 更新时间没变就跳过评论，也不能把缺页或网络失败记成没有变化。关键操作前还要重新核验依据。

为什么超时后不直接重试一次？

要先分清超时发生在哪一步。如果远端已经创建事项，只是回执丢了，再发一次就可能重复建单。程序应保存原操作身份，去远端核对后再继续。尚未执行的待办可以等待恢复；缺少有效查重依据的任务，则需要新的查询和判断。

Issue 还开着，能说项目完成了吗？

要说明完成到哪一层。当前两条案例完成了需求评审和可运行演示，并有对应测试与回报；它们没有因此进入真实 Octo 生产环境。PRD ready、演示验收、代码合并和生产发布各有条件。保留 Issue 打开，正是在避免把演示完成误写成功能上线。

HTTP 测试和浏览器测试到底差在哪里？

HTTP 测试直接请求后台，检查权限、数据和错误处理。浏览器测试从按钮和输入框走用户路径。#10 第四版只有放慢输入才发现刷新覆盖草稿；第五版静态检查通过，后端页面却因请求头不符合预览桥协议而失败。这说明还要分清版本、操作速度和运行模式。第六版的独立 HTTP 7 项、可信后端浏览器 30 项、静态浏览器 25 项分别通过，旧版失败与统计仍保留。

证据：v2 浏览器反馈、v3 一致性反馈、v6 最终交付。

转人工是不是意味着系统只能停在那里？

某个阶段缺少关键事实或决定时，要明确留下缺口并找配置负责人。其他可以调查、恢复或处理的工作仍按各自状态继续。求助通知发出后，不能假设人已经接手；当前并没有用这条通知冒充完整的人工接手工单流程。

三知识仓、ATE、协作治理参考项目 到底贡献了什么？

三知识仓提供资料分层、权威来源和交接方法；ATE 帮助组织角色、输入输出、交接和工作区投影；协作治理参考项目 提供证据分级、独立复核和如实说明完成范围的经验。我们选择性采用这些方法，再对接真实平台。这里没有把只读参考说成整套安装，也没有证据表明私人 Linux 事实库直接成为产品的在线知识服务。

V2 更完整，为什么选 MVP？后来五角色是不是又回去了？

V2 的设计覆盖更广，实际需要接通和验证的组件也更多。当时用户选择先缩小运行范围，完成三角色的真实业务。后来增加开发和独立测试，是因为需要可操作演示；它们沿用已有插件和业务库。角色回到五个，不代表重新引入了 V2 的全部框架。

有 Docker 以后，为什么还要管宿主文件和浏览器？

因为代码会在不同位置执行。Docker 限制 Agent 的命令环境；宿主插件还会收集产物并发布，必须自己检查路径与内容；生成的 JavaScript 到了用户浏览器，又需要浏览器层面的限制。一个位置的检查通过，不能替另外两个位置作证明。

现在可以说连续红队和新安全预览已经全部通过吗？

不能合在一起说全部通过。当前 #9 v2、#10 v6 已完成演示交付，防护修复已安装，六个旧预览已迁移并完成公开读回。真实凭证相关输入发送 14 条，检查 13 条输出，第 14 条只查完成状态；原定 20+ 目标未完成。后续 12 条合成另列，其中没有执行文件读取的项目不算文件边界通过。5 条普通群控制中 3 条通过，2 条初始失败保留。另有 5 次 Bot 私聊被 not_friend 挡在发送前，既没有 Agent 运行，也不能计为通过或 Agent 失败。已检查的历史输出未观察到真实凭证泄漏，结论限于该批样本。

可以宣传节省了多少成本，或者说这是行业首创吗？

目前可以报告固定合成场景的请求变化，以及选定真实运行样本，不能把它们外推为整体生产成本收益。项目的亮点可以具体说：程序管理阶段与外部动作，Agent 自主调查，独立评审和实际操作推动纠错。已有方法的借鉴关系也讲清楚，不需要用未经核实的首创或节省比例支撑价值。
