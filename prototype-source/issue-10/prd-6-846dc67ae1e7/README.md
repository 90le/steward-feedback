# 提醒 · 稍后再提醒（snooze）原型 · PRD v6 / 候选 r1

对应 PRD：`steward-feedback#10` v6。这是**演示原型**，用于让评审者与独立测试者从用户视角观察 R1–R17 / AC1–AC21 的可感知行为，不是真实 Octo 功能。

## 启动方式

```bash
# 无依赖，仅使用 Node 24 内置模块
node server.mjs
# 或指定端口
PORT=8080 node server.mjs
```

启动后：

- 打开 `http://127.0.0.1:3000/`，进入联调（后端）模式。此时 `<html data-api="1">` 由服务器注入，前端会调用同源 `/api/*`。
- 直接双击 `index.html` 或在纯静态托管下打开，进入**本地模拟模式**：前端不 fetch，操作只作用于当前浏览器标签页的内存数据（用于查看 UI）。

## 与 v5 的差异（针对 v6 反馈）

1. **R16/AC20 — 可信预览入口能真实加载提醒**：v5 版本前端 fetch 时附带了 `Accept: application/json` 头。预览包装的窄桥仅允许 `Content-Type`、`X-User-Id`、`X-Acting-User` 三类 header；额外的 `Accept` 头会被拒绝，导致可信预览入口打开后提醒列表始终空白。本版仅发送允许的 header：GET 只发 `X-Acting-User`，写入接口另加 `Content-Type: application/json`。同源 Node 服务下不受该限制，两种入口（可信预览 + 本地 `node server.mjs`）都能读取到本人提醒。
2. **R17/AC21 — 可见快捷项不再产生过去时间**：v5 提供的 `+5s` 快捷项在分钟粒度输入框下被截断到当前分钟起点，点击后极易变成"不晚于当前时间"。本版移除 `+5s`，仅保留能稳定产生未来时间的 `+15 分钟 / +1 小时 / +1 天`；输入框改为 `step="1"`（秒级），快捷项在**点击时**基于服务器最新时钟计算目标点，进一步防止取值瞬间跨过当前时间。此外仍保留服务端 `> now` 的权威校验（AC7/AC13/AC18）。

保留 v5 已修好的编辑输入保持（R13/AC17）、无效输入可继续修改（R14/AC18）与失败保留状态（R15/AC19）逻辑；既有 `data-testid`、身份切换、原消息真实定位、跨入口一致性均未改动。

## 后端接口（仅演示，全部读取内存中的模拟数据）

所有 `/api/*`（除 `/api/health`）都需要 `X-Acting-User` 头（`u_alice` / `u_alice2` / `u_bob`）。`u_alice` 与 `u_alice2` 代表**同一个人**的两个入口/端，用来观察 R9/R12 与 AC15/AC16 的跨入口一致性。

| 方法 | 路径 | 作用 |
| ---- | ---- | ---- |
| GET  | `/`  | 返回 `index.html` 并注入 `data-api="1"` |
| GET  | `/api/health` | 健康检查（无需身份） |
| GET  | `/api/reminders` | 列出本人当前的提醒（含 `state=active/snoozed/done`） |
| POST | `/api/reminders/:id/snooze` | JSON `{snoozeUntil: <毫秒时间戳>}`；服务器校验 `> now`，失败保持原状态 |
| POST | `/api/reminders/:id/cancel` | 取消延后，立即恢复为 active |
| POST | `/api/reminders/:id/done`   | 明确标记已处理，同时取消延后（R9） |
| GET  | `/api/reminders/:id/message` | 返回原消息与所在会话切片，用于真实定位 |

服务器对每个变更接口都做身份与业务校验：他人的提醒返回 403（R6/AC9）；`snoozeUntil <= now` 返回 400 并附带 `now`（AC7/AC13/AC18）；已 done 的提醒不能再 snooze。

## 模拟身份

| 入口 ID | 说明 | 后端映射 |
| ---- | ---- | ---- |
| `u_alice`  | Alice · 入口 A（例如手机） | 本人 = `u_alice` |
| `u_alice2` | Alice · 入口 B（同一人的网页端） | 本人 = `u_alice` |
| `u_bob`    | Bob · 同群其他成员 | 本人 = `u_bob` |

## 建议的用户视角走查（对应 AC）

1. **AC1 / R1**：以 `u_alice` 打开，对 `r_a_1` 点「稍后再提醒」，选择 `+15 分钟` 并确认。该提醒立即从"未处理"移动到"已延后"。
2. **AC3 / R3 / AC14**：手动把某条延后时间改到 10 秒后（在编辑框秒位调），到期后刷新，提醒回到活跃列表。点「查看原消息」，右侧原会话真实展示并**高亮**对应消息。
3. **AC4 / AC5**：延后中修改时间、取消延后，观察列表实时变化。
4. **AC7 / AC13 / AC18**：编辑框把时间改成过去时间，点确认——弹出错误提示，**输入保留在编辑框中**，可直接修改后再确认；界面没有"已保存"文字。
5. **AC9 / R6 / AC2 / AC12**：切换到 `u_bob`，只能看到 Bob 的两条；Alice 的操作不影响 Bob。
6. **AC10 / AC11**：Alice 先对 `r_a_2` 延后，然后立刻点「标记为已处理」；到达延后时间不再出现（AC10）。若不点已处理只「查看原消息」，到点仍会重现（AC11）。
7. **AC15 / AC16**：Alice 在入口 A（`u_alice`）标记已处理，切换到入口 B（`u_alice2`）刷新，看到同一提醒已为已处理。
8. **AC17 / R13**：打开编辑框输入一个时间后静置 ≥6 秒（每 3 秒自动刷新一次），输入框内容保持不变；确认时保存的就是刚才看到的值。
9. **AC20 / R16**：通过可信预览入口打开，同样能看到本人的提醒列表并操作；不再出现"入口打开但列表始终空白"。前端仅发送预览窄桥允许的 header。
10. **AC21 / R17**：依次点击 `+15 分钟 / +1 小时 / +1 天`——填入值均严格晚于当前，确认保存均成功；不再出现"点了可见快捷项却被'时间必须晚于当前时间'拒绝"。

## 与真实功能的边界

- **只是原型**：所有数据在进程内存中，服务重启即清空。没有真实群消息、通知或推送。
- **身份是模拟的**：`X-Acting-User` 头是不带鉴权的入口标识，仅用于演示同一人多入口一致性；不接任何真实用户系统。
- **不改上游**：不修改任何 octo-server 源码或调用其真实 API；仅在本地 HTTP 服务上演示。
- **PRD 未固化的开放问题（OQ1–OQ13）** 在原型里都用保守默认展示（例如快捷项 `+15m/+1h/+1d`、任意秒级 datetime 输入），仅作为可观察演示，不代表已被决定。
- **沙箱预览包装限制**：真实预览环境中，表单不能靠原生 submit 事件路径；本原型全部使用 `type="button"` + click 处理，未使用原生表单提交、页面跳转、localStorage、iframe 或跨域资源；仅使用允许的三类 header。
